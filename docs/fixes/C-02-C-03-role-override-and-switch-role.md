# C-02/C-03: Remove the role-override cookie and the switch-role endpoint

- Severity: CRITICAL
- Audit reference: C-02 "A browser cookie overrides any user's role" and C-03 "`POST /api/auth/switch-role` requires no login and writes to the database" (§3 Authentication and authorization)
- Status: Fixed
- Date: 2026-11-23

## Problem

`src/lib/auth.ts` resolved the session role from a browser cookie instead of
from the session's membership row. Before this fix, `getTenantContext` read:

```ts
const testRole = cookieStore.get("active_test_role")?.value as UserRole | undefined;
const finalRole = (testRole && ["owner", "admin", "team", "expert", "member"].includes(testRole))
  ? testRole
  : ((row.userRole as UserRole) || "team");
```

No cookie is `httpOnly` from the browser's perspective when an attacker sets it
by hand, so any authenticated member could send `active_test_role=owner` and
pass the owner checks at `src/app/api/business/delete/route.ts:19` and the
admin check at `src/app/api/admin/businesses/route.ts:13`.

`src/app/api/auth/switch-role/route.ts` set that cookie and also wrote role
changes straight to the database:

```ts
const tenant = await getTenantContext();
...
await db.update(memberships).set({ role }).where(...);
await db.update(users).set({ role }).where(eq(users.id, tenant.userId));
...
response.cookies.set("active_test_role", role, { ..., httpOnly: false, ... });
```

It had no session check, role check, or elevation guard. After C-01 landed, the
anonymous path throws before the write, but any logged-in member could still
POST `{"role":"owner"}` and change their own `memberships.role` **and** the
global `users.role` used by login (`src/app/api/auth/login/route.ts:95`).

## Root cause

A localhost RBAC-testing persona switcher was wired into production
authentication. The role that gates authorization was read from a client-
controlled cookie, and a separate unguarded endpoint mutated the authoritative
role rows to make the switch "stick". Neither path checked that the caller was
an owner, so the test affordance was a working privilege-escalation primitive.

## Fix

Both issues had to ship together: removing only the cookie reader would leave
the DB self-promotion endpoint, and removing only the endpoint would leave the
hand-settable cookie.

Files changed:

- `src/lib/auth.ts`: deleted the `active_test_role` read and `finalRole`
  override in `getTenantContext`; the role now comes only from
  `(row.userRole as UserRole) || "team"` in the session lookup.
- `src/app/api/auth/switch-role/route.ts`: **deleted** (directory removed). With
  the override gone, the cookie it sets is inert and its DB write is
  unauthorized by design, so there is no safe behavior left for it. A no-op
  `200` would mislead clients; a `410` stub would keep an attack surface and
  dead UI controls.
- `src/components/layout/AppShell.tsx`: removed the `switchingRole` state, the
  `switchRole` handler, the "Switch Role (RBAC Testing)" control block, and the
  "Switch to Owner (Test Mode)" button on the access-denied screen. Role labels
  and route gating remain driven by `/api/auth/context`.
- `src/app/settings/roles-prompts/page.tsx`: removed `handleSwitchRoleLive`,
  its state and toast, and the five "Test Role" buttons in the security
  matrix. The matrix itself is unchanged.
- `scripts/verify_rbac_roles_and_otp.py`: removed only the switch-role calls
  (old lines 42–108) and the assertions that depended on them; renumbered the
  remaining screen check to Check 3 and the final count to 3. No other script
  behavior was changed.
- `tests/c02_c03_role_override.test.ts`: new test file (see below).
- `docs/fixes/C-02-C-03-role-override-and-switch-role.md`: this document.

No dependency added, no database schema change. The stale generated
`.next/types/` cache was removed after deleting the route (it is gitignored and
regenerated by `next build`/`next dev`); this is not a source change.

## Risks and follow-up

- **Public API contract change (approved):** `POST /api/auth/switch-role` is
  removed; any client calling it now receives 404. Both in-repo callers were
  updated in the same change.
- **Testing gap:** the two UI removals have no component tests, and
  `scripts/verify_rbac_roles_and_otp.py` no longer verifies RBAC at all — it
  switched roles with a single session. Proper coverage needs separately
  seeded users with one role each and their own sessions, which is follow-up
  work, not something this change can substitute.
- Existing browsers may still hold an `active_test_role` cookie. It is now
  inert (no reader), but `src/app/api/auth/logout/route.ts:17-18` still does
  not delete it — H-08 remains open.
- A real "view as role" preview would need server-side session state (a
  schema change and a product decision) and must be restricted to the actual
  owner; it is deliberately not implemented here.
- C-09 (a shared `requireSession()` guard on every route) and C-20 (role
  enforcement on mutating routes) are still open. Removing this endpoint does
  not make the remaining write endpoints authorize.
- `src/app/api/auth/login/route.ts:95` still defaults a user with no
  membership to `owner` (H-09); not touched here.

## Newly found (not fixed)

- `src/components/layout/AppShell.tsx:70-86`: the signed-out redirect gate
  depends on `fetch("/api/auth/context")` returning JSON. Since C-01 made that
  route fail closed for anonymous callers, the response is a 500 and the
  `.catch` only logs — the redirect never happens. Combined with
  `src/components/layout/AppShell.tsx:51-57`, which defaults `currentTenant` to
  the Acme owner, the shell can display the demo owner to signed-out visitors.
- `scripts/verify_rbac_roles_and_otp.py:9, 136`: the banner and final summary
  still advertise "RBAC" verification, but after removing the switch-role
  section the script performs no role checks. Its name, banner, and final
  message are now misleading until real multi-user RBAC checks are added.
